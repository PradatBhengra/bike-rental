# Bike Rental Phases 1–5 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build phases 1–5 of the design: accounts, rentals, Razorpay payments with jobs and events, analytics, and the RAG chatbot, plus the files for the first deployment.

**Architecture:** One FastAPI app (`api/app`) split into modules that call each other only through service functions. A `worker` process (same image, `python -m app.worker`) runs the outbox dispatcher, the job queue and the scheduled checks. Postgres holds everything, including events and jobs. Redis holds rate limits, the availability cache and pub/sub. The React app in `web/` talks to `/api/v1`.

**Tech Stack:** Python 3.13, FastAPI, psycopg 3 (plain SQL), dbmate, Postgres 17 + PostGIS + pgvector + btree_gist, Redis, PyJWT, bcrypt, Razorpay (httpx), openai SDK → Groq / OpenRouter, fastembed (bge-small-en-v1.5, bge-reranker-base), Garage via boto3, Mailpit, WeasyPrint; React, TypeScript, Vite, React Router, TanStack Query, Tailwind, Recharts, react-leaflet, openapi-typescript; pytest, testcontainers, Vitest, ruff, ESLint, Prettier.

## Global Constraints

- Money is integer paise; times are `timestamptz`; ids are `bigint` identity; daily figures use the `Asia/Kolkata` day.
- Service functions take `conn` as the first argument; routes and job handlers own the transaction (`with db.tx() as conn`). Time-dependent services take `now` so tests and the seed can set the clock.
- Booking statuses: `pending_payment, confirmed, picked_up, returned, cancelled, expired, no_show`; only `bookings.transition()` changes them, writing history and an outbox event in the same transaction.
- Exclusion constraint `EXCLUDE USING gist (bike_id WITH =, during WITH &&) WHERE (status IN ('pending_payment','confirmed','picked_up'))`.
- Access token 15 minutes, in memory; refresh token 14 days in an httpOnly `SameSite=Strict` cookie, rotated with family revocation on reuse.
- Errors are `application/problem+json` (RFC 9457). REST lives under `/api/v1`.
- Hold, grace periods and refund tiers live in `setting`; the documents state the same numbers and a test compares them.
- The model never writes: `propose_*` tools create `chat_action` rows; only `POST /chat/actions/{id}/confirm` executes. Personal tools take the user id from the token.
- At most 5 tool steps a turn; small model first, big model once `search_docs` is called or after 2 steps.
- No git commits unless the user asks (user preference; replaces the template's commit steps).
- Plain code: few helpers, no speculative abstraction.

## Review Focus

1. Two tabs refreshing with the same refresh token at once: the browser must send one refresh, or reuse detection logs the user out. Test: `web/src/api/client.test.ts` concurrent `refresh()` calls make one request.
2. A Razorpay payment that lands after the hold expired: the booking stays `expired` and the payment is refunded in full. Test: `test_payments.py::test_payment_after_hold_expired_is_refunded`.
3. A password longer than bcrypt's 72 bytes: a 422, not a 500. Test: `test_auth.py::test_password_over_72_bytes_rejected`.
4. Booking times with no timezone, outside opening hours, or ending before they start: a 422 that says why. Test: `test_bookings.py::test_booking_time_validation`.
5. A chat question that is all stopwords: keyword search returns nothing instead of an SQL error, and vector search still answers. Test: `test_retrieval.py::test_stopword_only_query`.
